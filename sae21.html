SAÉ 2.01

Construire un réseau informatique pour une petite structure

Introduction

Dans le cadre de la SAÉ 2.01 « Construire un réseau informatique pour une petite structure », j'ai travaillé sur la mise en place progressive d'un environnement réseau composé de plusieurs machines virtuelles.

L'objectif de cette première étape était de préparer les machines et de vérifier leur capacité à communiquer sur un même réseau avant de poursuivre la configuration des services réseau et l'administration du serveur.

J'ai utilisé VirtualBox afin de créer un environnement de travail isolé. Une machine Windows Server 2022 a été utilisée comme serveur et une seconde machine Windows comme poste client.

Apprentissages critiques

Cette première situation m'a principalement permis de travailler les apprentissages critiques suivants :

  • AC11.03 — Configurer les fonctions de base du réseau local.
  • AC11.04 — Maîtriser les rôles et les principes fondamentaux des systèmes d'exploitation afin d'interagir avec ceux-ci pour la configuration et l'administration des réseaux et services fournis.
  • AC11.05 — Identifier les dysfonctionnements du réseau local et savoir les signaler.

Ces apprentissages sont directement liés au descriptif de la SAÉ 2.01, qui demande notamment de construire une architecture réseau et de mettre en place une méthode permettant de tester progressivement la configuration réalisée.

Travail réalisé

Pour commencer le projet, j'ai créé deux machines virtuelles dans VirtualBox. La première machine utilise Windows Server 2022 et la seconde utilise Windows Client.

Afin de permettre aux deux machines de communiquer sans les mélanger avec le réseau réel, j'ai configuré leurs cartes réseau sur un même réseau interne VirtualBox nommé SAE21.

Configuration du serveur

  • Système : Windows Server 2022
  • Adresse IPv4 : 192.168.50.10
  • Masque : 255.255.255.0
  • Réseau VirtualBox : SAE21

Configuration du client

  • Système : Windows Client
  • Adresse IPv4 : 192.168.50.11
  • Masque : 255.255.255.0
  • Réseau VirtualBox : SAE21

Problème 1 — Impossible de communiquer entre les deux machines

Situation

Après avoir configuré les deux machines virtuelles sur le même réseau interne, j'ai voulu vérifier leur communication avant de continuer la configuration du serveur.

Le serveur possédait l'adresse 192.168.50.10 et le client l'adresse 192.168.50.11.

Les deux machines utilisaient également le masque 255.255.255.0. Elles se trouvaient donc dans le même réseau IPv4.

Le problème rencontré

J'ai effectué un test de communication depuis le serveur vers le client avec la commande :

ping 192.168.50.11

Malgré la configuration correcte des adresses IP, le serveur ne recevait aucune réponse du client.

Le résultat affiché était :

Délai d'attente de la demande dépassé.

Constat

Le problème ne semblait donc pas provenir directement de l'adressage IP. Il fallait déterminer pourquoi les requêtes de test n'étaient pas reçues par la machine distante.

Analyse du problème

Pour éviter de modifier plusieurs paramètres en même temps, j'ai procédé par étapes afin d'identifier précisément l'origine du dysfonctionnement.

1. Vérification de l'adressage IP

J'ai commencé par utiliser la commande ipconfig sur les deux machines.

ipconfig

La configuration était correcte :

  • Serveur : 192.168.50.10/24
  • Client : 192.168.50.11/24

Les deux machines appartenaient donc au même réseau 192.168.50.0/24.

2. Vérification de VirtualBox

J'ai ensuite vérifié la configuration des cartes réseau dans VirtualBox.

Les deux machines utilisaient le même réseau interne : SAE21.

J'ai également vérifié que les cartes réseau virtuelles étaient activées et que le câble virtuel était connecté.

3. Recherche de la cause

Après ces vérifications, l'adressage et la configuration du réseau virtuel étaient corrects. Le problème se situait donc au niveau du système d'exploitation.

Les requêtes ICMP utilisées par la commande ping étaient bloquées par le pare-feu Windows.

Le serveur et le client pouvaient donc être correctement configurés sur le même réseau tout en refusant les requêtes ICMP entrantes.

Résolution du problème

Pour résoudre le problème, j'ai choisi de ne pas désactiver complètement le pare-feu Windows. J'ai plutôt créé une règle permettant uniquement les requêtes ICMPv4 nécessaires aux tests de connectivité.

Création de la règle de pare-feu

Depuis PowerShell exécuté avec les droits administrateur, j'ai utilisé la commande suivante :

New-NetFirewallRule -DisplayName "SAE21 - Autoriser ICMPv4" -Protocol ICMPv4 -IcmpType 8 -Direction Inbound -Action Allow

Cette règle autorise les requêtes ICMPv4 de type Echo Request entrantes. Ce sont les requêtes utilisées lorsqu'une machine effectue un ping.

Nouvelle vérification

Après avoir appliqué la règle, j'ai relancé le test depuis le serveur vers le client :

ping 192.168.50.11

Cette fois, le serveur a reçu des réponses du client. La communication entre les deux machines était maintenant fonctionnelle.

Ce que cette situation m'a appris

Cette première difficulté m'a permis de comprendre qu'une configuration IP correcte ne garantit pas nécessairement qu'une communication réseau sera possible.

J'ai appris à distinguer plusieurs niveaux de diagnostic : l'adressage IP, la configuration du réseau virtuel et les règles de filtrage du système d'exploitation.

J'ai également compris qu'il est préférable d'identifier précisément la cause d'un problème plutôt que de désactiver complètement un mécanisme de sécurité.

Cette situation m'a donc permis d'adopter une démarche plus méthodique : observer le problème, vérifier les différentes hypothèses, identifier la cause, appliquer une correction ciblée puis vérifier le résultat.

Compétence(s) développée(s)

  • Configurer une adresse IPv4 et un masque de sous-réseau.
  • Mettre en place un réseau interne entre plusieurs machines virtuelles.
  • Utiliser ipconfig pour vérifier une configuration réseau.
  • Utiliser ping pour tester la connectivité entre deux machines.
  • Identifier un problème de filtrage réseau lié au pare-feu Windows.
  • Créer une règle de pare-feu avec PowerShell.
  • Vérifier le fonctionnement du réseau après une modification.

Analyse réflexive

Au début du diagnostic, je me suis concentré principalement sur les adresses IP des deux machines. Cette vérification était nécessaire, mais elle ne permettait pas à elle seule d'expliquer le problème.

J'ai ensuite appris à élargir mon raisonnement en vérifiant également la configuration du réseau virtuel et les mécanismes de sécurité du système d'exploitation.

Cette situation m'a montré qu'en administration réseau, il est important de procéder étape par étape et d'éviter de modifier plusieurs paramètres simultanément.

Cette méthode permet de mieux comprendre l'origine d'un dysfonctionnement et de vérifier que la solution appliquée répond réellement au problème rencontré.

Autoévaluation

Je considère que cette première situation m'a permis de renforcer mes bases en configuration réseau et en diagnostic.

Je suis maintenant capable de configurer une communication réseau simple entre deux machines virtuelles, de vérifier leur configuration IP et d'utiliser des outils de diagnostic comme ping et ipconfig.

Je dois cependant continuer à pratiquer l'administration des services Windows et l'analyse des règles de filtrage afin de gagner progressivement en autonomie.
